### Traps for BC-11 and BC-12

- A unique index on `ItemId` fails if the db already holds a duplicate. Check a copy of
  the host's db for duplicate ItemIds before writing migration 45.
- A failed migration doesn't stop the app. `Migrate()` sits in a try/catch in
  `Program.cs`; it prints one line and the app keeps serving on the old schema
  (Front_Load A11). A migration that fails on the host can go unnoticed.

## How to work here

- A routine fix to an existing pattern: build it. A new mechanic: write back the whole
  scope (every field, every gate, every edge case) and wait for my yes before opening a file.
- Never commit or push unless I say.
- Never start the app against `C:\VIS_Inventory\inventory.dev.db`, `C:\VIS_Inventory\inventory.db`
  or the host's db. It migrates on start. Use a scratch copy:
  `--ConnectionStrings:DefaultConnection="Data Source=<copy>"`.
- `dotnet build` after every real chunk. Baseline: 0 errors, 14 warnings (an incremental
  build reports fewer; that isn't a change).
- Views are compiled into the DLL, so restart the app to see a view change.
- Comments short, label style. Reasoning and history go in `docs/Code_Notes.md`. View
  comments are Razor `@* *@` only, so none reach the browser.
- "Non-TC Motor", never "plain motor".
- Docs in `docs/` are in my first-person voice. A fix gets logged in `Bug_Checks.md`
  (row + status paragraph), a `VIS_Debugging_Log.md` entry, `Code_Notes.md` for each file
  touched, the handoff's "Still to do", and `Commit_History.md` when it's committed.
- Files mix CRLF and LF. Edit in place; no whole-file rewrites.
- Reproduce a bug on the current build before fixing it, and check the fix the same way,
  in the running app on a scratch copy.
